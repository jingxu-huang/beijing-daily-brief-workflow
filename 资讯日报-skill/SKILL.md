# 出海泛娱乐 资讯日报 Skill

新 Mac 恢复或用户要求“一键重启 skill”时，先读 [`../docs/运行与交接手册.md`](../docs/运行与交接手册.md)，从工作流仓库根目录运行 `bash bootstrap_new_mac.command` 完成基础安装、账号授权和公开源，再核对两个固定飞书索引的登记与权限，最后运行 `bash automation/install_parallel.command` 安装正式守门器和测试矩阵。不得把“基础安装完成”冒充“飞书正式/测试双链路已验收”。WeWe RSS、WeRSS、wechat-download-api 当前均不作为在役输入；WeRSS 历史探测代码保留，但未经单独批准不得通过配置重新启用其后台链路。

当任务涉及 Skill 来源、规则演化、公众号渠道替代、历史失败原因或移交复盘时，再读 [`../docs/Skill历史与公众号源迭代.md`](../docs/Skill历史与公众号源迭代.md)。它区分可追溯 Git 提交、Git 外私有测试证据及仅讨论过的方案；历史登录/抓取步骤不是当前执行授权。

当前并行合同：正式版始终使用默认 `legacy` 策略和独立生产目录；测试版在北京时间 15:00 关窗后只抓取一次共同原始快照，隔离并行生成严格、平衡、高召回三篇，三版共同使用同一来源窗口。正式版绝不读取测试快照或测试版筛选配置，测试版绝不写正式成稿/索引。正式日报及正式索引授战略小组 `full_access`，三篇测试日报及测试索引授 `edit`；均不发群消息。任何 QA `FAIL`、索引原位写入或授权失败，必须报告失败，不能称作交付完成。具体脚本、状态文件、飞书索引地址和恢复步骤以交接手册为准。

把"抓取 → 过滤 → 浓缩 → 排版 → 校验"沉淀成一条可每日重复、可移植（Claude Code / Codex 等都能跑）的流程。

## 适用场景
- 公司主营出海泛娱乐，需每日产出固定格式的资讯简报。
- 覆盖三大板块：泛娱乐·出海、创新·AI娱乐、全球融资。

## 需求基线（给 Codex / 任何 agent 复现，逐条满足）
1. **时间维度**：仅取北京时间（Asia/Shanghai）「前一日15:00（含）— 当日15:00（不含）」的资讯；抬头注明该时间范围。脚本默认按此左闭右开滚动窗口（`bj_window`），所有业务时间由可信 UTC 换算，不跟随电脑显示时区或手动墙钟漂移。
1a. **历史日期测试**：如需测试过去某天，运行 `python fetch_news.py --date YYYYMMDD`；窗口仍为北京时间「前一日15:00（含）— 当日15:00（不含）」。列表页源会先进文章页解析发布时间并按窗口过滤；仍无时间戳的 listpage 默认不进入精选/备选正式候选，但会出现在草稿末尾「列表页无时间戳排查」区，避免把当前列表页或旧文误当成当日新闻，同时保留人工核验线索；只有明确排查抓取问题时才加 `--include-undated` 临时放回候选区。
1b. **跨日链接回溯**：抓取时自动回溯前 2 天草稿/成稿链接；若 URL 已在前 2 天出现，本日不再新增。
2. **三大板块 + 赛道**：泛娱乐·出海（休闲游戏/短剧/漫剧/小说·网文/社交·Dating/其他）、创新·AI娱乐（AI模型与应用/创新硬件）、全球融资（泛娱乐融资/泛AI·AI应用融资）。无内容的赛道省略。
2a. **主题准入（宁缺毋滥，治"无关混入"）**：每条先判定其**正文主体**是否属于三类之一——① 出海泛娱乐（游戏/短剧/漫剧/网文/社交·Dating/IP/泛娱乐内容及其业务·财报·数据）；② 娱乐向 AI（面向内容/娱乐/消费者的 AI 模型·应用与创新硬件）；③ 泛娱乐 / 泛AI·AI应用融资。不属于的**直接丢弃**。明确**排除（OUT）**：纯跨境电商/品牌卖货（服装、3C 等带货/选品/GMV）、宏观经济与监管约谈、电诈反诈等社会与政策/案件新闻、半导体/芯片股价行情、航天·火箭·卫星·太空算力、自动驾驶/Robotaxi/Robovan（属具身）、与娱乐无关的企业人事·财经杂讯、新闻早报/资讯聚合体（如《8点1氪》《早报》）。"其他"赛道只收**明确属于泛娱乐**但不在四个子赛道的内容，**不得当作无关内容的兜底桶**。
2b. **归类只看正文、不看来源（治"按渠道分类"）**：板块/赛道由该条正文实际在讲什么决定，与它来自哪个站点/feed 无关；来源仅用于取链接与文末 Source 表。**不得仅因正文出现某关键词（如"社交 App""AI"）就归入对应赛道**（例：一条电诈案件即便提到"社交 App 引流"，也不属于社交·Dating，应整条剔除）。
2c. **同一事件合并（治"同类项不合并"）**：同一主体 + 同一事件被多源报道时，合并为信息最全的一条，多来源链接并列；融资/榜单/财报尤其要合并，不要拆成多条。
2d. **行业大会/活动准入（治"会议预告泛滥"）**：只写"大会召开/报名/议程/嘉宾阵容/注册人数/活动回顾"、但没有实质行业观点、趋势判断、关键数据或公司策略信息的会议类资讯，默认不收。除非是 ChinaJoy 等行业级大会，且原文输出了可复用的行业观点或数据，否则不要占用正文位置；若只是日程信息或会务宣传，整条剔除。
2e. **业务关注提权信号（进入精选/备选复查时优先看）**：以下内容即使脚本 score 不高，也要人工提权复查，避免漏收：
   - **AI 营销 / AI 增长 / 达人带货自动化**：与广告投放、达人增长、营销自动化、带货链路、内容生成到转化效率相关的 AI 应用，属于营销增长类业务关注信号；如 K2Lab / Moras 这类案例，可按使用者业务画像提高优先级。
   - **高流水小游戏 / 小游戏矩阵 / 发行工厂模式**：不是普通单一休闲小游戏，而是具备高流水、矩阵化复制、混休/IAP 转型、发行工厂方法论的公司或产品，应明显高于普通小游戏新闻；如 Voodoo 日流水/矩阵变化。
   - **微信生态下的 AI 支付 / AI 交易基础设施**：微信支付、微信生态与 AI 消费/支付/交易结合的动态需要跟踪，即使不直接属于泛娱乐主题，也可作为交易基础设施动态提高可见度。
   - **头部模型关键进展（短条即可）**：只关注全球范围内最头部的模型或能力方向，尤其视频生成头部模型（如 Seedance）与 LLM/Coding 头部模型（如智谱 GLM 5.2 这类在 Coding 领域进入头部梯队的动态）。非头部、全球范围排不上号的模型不要因"模型发布"本身提权；入选时通常简短提一句即可，不必展开成长条。
   - **OpenAI 等头部 AI 公司关键财务/上市动态**：OpenAI 财报、现金消耗、上市前材料、重大融资等，即使不直接属于泛娱乐或具体应用，也值得保留一眼关注。
   - **大厂 AI 游戏/互动体验创作工具**：Meta、Google、OpenAI、字节、腾讯等头部平台推出的 prompt-to-game、AI 游戏创作、互动体验生成、UGC 小游戏/互动应用工具，属于大厂在互动娱乐上的产品布局，必须人工提权复查（例：Meta Pocket / Gizmo），不得因在备选池或标题看似“小工具”而漏收。
2f. **创新硬件准入（治"电竞外设/PC 发布混入"）**：「创新硬件（娱乐向）」只收形态或交互方式有明显变化的产品，例如 AR / VR / XR 眼镜、AI-native 硬件（如 Looki、未来智能 AI 耳机）、AI 鼠标 / AI 键盘 / AI 录音卡等以 AI 交互为核心的外设、体感/空间交互/游戏控制新形态、可穿戴或环境计算设备。普通游戏本、游戏台式机、电竞显示器、鼠标、键盘、耳机、电竞桌椅等参数型新品/联名款/上架发售新闻，默认不收；但若鼠标/键盘/耳机等外设的核心卖点是 OpenAI / ChatGPT / 大模型 / 智能体 / 实时翻译 / 转写 / 个人助理等 AI-native 能力，应保留复查，不得被普通外设规则误杀。
2g. **业务相关性测试策略（`business_v1_test`）**：测试目标不是把日报泛化成泛娱乐大新闻，而是只保留能帮助公司判断产品、内容、竞争、增长、变现或 AI 应用机会的资讯。休闲游戏只收休闲/超休闲/混休/小游戏的产品、发行、买量、留存、流水或榜单，3A/主机/硬核 RPG/电竞赛事不收；短剧/漫剧收新玩家、海外爆款、区域/投放/订阅/内容工业化信息，单纯融资不收；硬件只收 AI 陪伴玩具、AI 键盘/耳机/眼镜、智能屏/家庭智能体等消费者 AI 交互产品，芯片、服务器、普通 PC/显示器等不收；融资不因“融资”或裸“上市”字样本身入选，只有明确资本动作且落到目标赛道才可保留。AI 模型与应用维持既有准入范围。
2g-1. **结构化判定与灰区**：`fetch_news.py` 必须输出 `accept / review / reject` 三态，以及分数、置信度、多标签、正反证据和正文完整度。单个宽泛排除词（如“机器人”）只能进入证据，不得直接删除已被产品形态和 AI 能力共同证明相关的候选；明确非休闲游戏、非 AI 普通硬件、非目标融资等多证据组合才允许高置信拒绝。正文不足时进入灰区，不得进入自动精选，也不得无声丢弃。
2g-2. **集中配置与双层 QA**：测试策略的业务信号、权重和 `accept/review` 阈值只在 `editorial_policy.yaml` 维护；成稿数量/来源/正文长度门禁仍只在 `sources.yaml` 维护。抓取阶段负责召回、结构化判定和同次重复合并；`check_report.py` 独立复核，高置信误收为 `FAIL`，灰区为 `WARN`，不得用同一宽泛词重复硬杀。每次运行把 accept/review/reject 审计账本写入 Git 外的 `日报状态/资讯日报-筛选审计-YYYYMMDD.json`，内部筛选理由不得写进日报正文。
2g-3. **启用边界**：必须显式使用 `--editorial-profile business_v1_test` 或环境变量启用，默认在役 `legacy` 日报保持既有策略。测试策略的硬门槛是最终成稿不少于 10 条、至少 3 个来源；数量不足必须报失败并扩展合格来源，不能以不相关资讯补数。
2g-3a. **并行筛选版本边界**：`business_v2_strict` 是当前要求的基准验收版，继续执行“正文不少于 10 条、无不相关内容”的硬合同；`business_v2_balanced` 与 `business_v2_recall` 仅用于比较漏选率，目标正文不少于 25 条。三版可共享短英文词边界、正文样板清洗、目标业务召回和排序修复，但不得用平衡版或高召回版的结果冒充严格版通过，且都不得用已明确不相关的内容补数。正式 `legacy` 默认值不变。
2g-3b. **测试版候选交付合同**：冻结草稿中的精选 URL 是必交集，精选+备选 URL 是成稿唯一允许集；灰区、已拒绝项和模型记忆不得在成稿阶段重新混入。同一事件多源可合并成一条，但必须保留所有已登记的独立来源 URL。严格版以 10 条为硬下限；平衡/高召回版在不降低安全门禁的前提下，必须按备选顺序主动向 25 条补选，安全池耗尽时允许低于目标。`check_report.py` 每轮都要输出可执行修复计划；即使结论为 `WARN`，只要必交 URL 缺失、成稿越界或尚有安全补位空间，就必须继续修复而不得提前终止。
2g-4. **测试版公众号通道验收**：公众号通道与成稿数量门禁独立记录。必须分别核验订阅列表、当前窗口文章列表和正文；空 RSS 外壳、复用旧快照或 `partial` 都不能冒充公众号链路通过。通道失败时允许继续生成纯公开源测试成稿，但 manifest 和质检必须保留脱敏 `WARN`，不得宣称全功能通过。当前窗口确无新文可以是 0 条，前提是所有订阅源都完成了当次新鲜查询。
2g-5. **AI 低价值训练/测试专项门禁**：小团队或学术型模型训练、内部工程测试、单项 benchmark/评测、调查/指数/审计、研究方法和观点讨论，不得仅因“AI/模型”词命中而进入日报。全球头部模型厂商只有在文中同时具备“明确厂商 + 具名模型版本 + 具体训练/发布动作”时才允许单源保留；娱乐向创作工具、AI 游戏应用和消费者 AI 硬件仍按原有业务规则判定，不受该研究门禁误杀。
2g-6. **AI 训练事件多源豁免**：非头部厂商的具体训练/模型发布事件，只能在同一窗口被至少两个独立真实发布者报道后提权。同事件必须同时满足：不同发布者、不同 canonical URL、完全相同的模型名/版本、相同的训练或发布动作，以及共享主体或足够的标题重合；泛化“AI 训练”词、相似主题或同一转载链路不计多源。两条确认稿必须合并为一条，选择正文更完整的版本并在草稿保留另一条佐证链接。调查、审计、方法讨论等非具体模型进展不得使用多源豁免。
2g-7. **v2 筛选执行合同（防止误杀）**：`fetch_news.py`、草稿补位与 `check_report.py` 必须调用同一份结构化决策，记录 `accept / review / reject`、理由、证据、正文状态和同事件佐证数。硬拒绝仅用于已明确无关的题材（非休闲硬核游戏、普通硬科技/基础设施、非目标融资，以及小型训练/跑分/测评）；政策、报告、活动、传闻和标题不完整等不冒充“无关”，进入可审计的 `review/hold`。 “不是目标应用”“只有一个来源”本身不得成为 AI 产品、具名模型正式发布、消费者 AI 硬件或目标融资的拒绝理由。多源规则只适用于小型训练/评测事件的例外放行。严格版不自动采用 review；平衡版可扩展正文完整的 `high` 与 `medium_safe` review；高召回版可再扩展 `medium` review。三版必须从同一份“时间窗+关键词召回后、编辑判断前”的原始快照回放；RSS 摘要过短但初判非拒绝时可在冻结前限量补取公开原文，补取状态和字数变化必须一并写入快照与审计，回放阶段禁止重新联网或用旧草稿冒充共享输入。
2g-8. **v2 融资企业速览（测试专用）**：仅 `business_v2_strict`、`business_v2_balanced`、`business_v2_recall` 的全球融资条目，写作前可由 Codex 检索并补充被投方的“主营/商业模式 + 最近公开估值”。正文只使用一条紧凑速览，不增加列表或编辑解读；所有补充事实必须落入 Git 外的 `日报状态/测试版-融资企业资料-YYYYMMDD.json`，逐字段保留来源 URL、发布方和检索时间。资料不足时如实写“公开资料未明确披露其主要变现方式”或“公开估值暂未披露”，不得用模型记忆、搜索摘要、融资金额或行业惯例推断。具体模板与字段见 `format/测试版融资补充规范.md`。正式 `legacy` 版本保持现有模板 C，不读取、不要求该资料文件。
3. **单条体例**：简明标题 → 正文（按信息量忠实浓缩，通常 200–400字，正文最后一个信息点末尾必须加来源名括注，如 `（IT之家）` / `（白鲸出海）` / `（DataEye短剧出海）`）→ 原文链接（必带，仍放条目最下面）。融资走模板 C。详见 `format/格式规范.md`。
4. **只浓缩、不做阅读理解**：把原文已有信息（是什么、关键数据、各方说法）提炼出来，**不加入编辑自己的分析/判断/"解读"**；原文里的观点可转述并注明出处。
4a. **去 AI 感（措辞，必做）**：成稿读起来要像人写的新闻条目，不像 AI 复述。两条硬规矩：
   - **不用泛指转述**：禁止 `文章称 / 原文称 / 原文认为 / 文章提到 / 文章将其视为 / 公众号文章称 / 报道回顾称 / 节目摘要称 / 文中认为 / 文中把 / 文中提到` 这类不指名的转述壳。也不要把媒体动作写进正文开头，例如 `白鲸出海整理的... / 点点出海梳理了... / 罗斯基转载并整理了... / 白鲸出海转引... / 白鲸出海围绕...梳理... / 36氪深氪栏目披露... / Z Potentials 介绍...`。日报正文直接写新闻事实；只有必须交代数据或观点来源时，才用一次具体来源（如 `AppMagic 数据显示`、`AppsFlyer 给出的数据为`、`据36氪`）。
   - **不补"解读尾巴"/营销腔**：删掉原文没有、由你补的拔高句，典型句式 `这意味着… / 显示… / 反映… / 说明… / 将其放在…趋势中观察 / 对X而言，这仍是…的重要场景 / 提供了一个…样本 / 强调…的自然观感`。条目止于事实和数据，不替读者下结论；产品描述用中性词，少用 `异军突起、华丽、沉浸、气质介于…之间` 等文学化/广告化形容。
5. **具体产品粒度**：每天纳入若干"单个产品发布/更新"（IT之家/ProductHunt/ai-bot 提供）。
5b. **配图（克制但要准）**：榜单/数据图、以产品形态为亮点的产品截图，才配图；每条最多一张，写在正文后链接前 `![](图片URL)`，不得用 Markdown 表格拼图。其余不配图；微信来源图有防盗链不用；脚本没给候选图就不配。`report_images.py` 会在正文生成期间并行预取草稿候选图，正文 QA 通过后再由独立的只读视觉审核选择相关图片并确定性插入，正文写作模型不再负责猜图。正式飞书投递前，`send_to_feishu_cli.py` 会逐张下载远程图片到 Git 忽略的 `.staging/`，必要时携带该条原文链接作为 Referer，再通过本地图片语法上传飞书。图片格式按实际字节签名识别；白鲸旧域名失败时自动改试当前域名。所有候选仍失败、返回 HTML、空文件、损坏或不支持格式时，从飞书发布副本移除该图片、保留完整正文，并写脱敏告警；图片层失败不重写正文、不改变正文 QA 结论，也不能留下灰色失败占位。已成功本地化的图片仍须在发布后逐张回读并做 SHA-256 一致性校验。
5c. **配图正文相关性/图像识别（独立媒体阶段）**：正文 QA 通过后，对已安全下载到本机工作区的候选图做视觉核验，确认图片确实对应正文核心对象。合格图片包括产品内截图、游戏实机画面、真实硬件/产品图、榜单截图、数据图表；不合格图片包括文章封面装饰图、Web 端首页/落地页截图、氛围图、泛用公司宣传图、公司 logo、与正文产品或数据无关的配图。国外媒体常用与正文无关的美化封面，不能因为它是首图就直接采用；无法确认相关性时宁可不配图。审核超时或失败只在 manifest 的 `images` 步骤记 `WARN`，不得阻断文本成稿。
5c-1. **配图选择优先级**：产品/游戏条目优先选能看出核心玩法、交互界面或应用内 UI 的图，App Store / Google Play / Steam 商店截图优先于媒体封面。数据报告优先选能概括标题核心数字的总览图；标题同时强调榜单、Top 10、区域对比等第二核心信息时，也只选一张最能代表正文主事实的总览或明细图。白鲸/Sensor Tower 报告优先使用总览卡或关键数据页，不默认使用首张文章封面。若一条正文同时覆盖多个具名产品/游戏，需先核对候选图与正文主对象一致，再选一张最具代表性的产品图；不能用表格或多图堆叠代替取舍。
5d. **配图覆盖与可用性自查（独立媒体阶段）**：正文 QA 通过后逐条核对——凡榜单/数据类（手游收入榜、短剧投放周榜、收入/流水数据等）与"以产品形态为亮点"的产品条目，草稿给了可下载且经视觉审核合格的候选图就配上一张。白鲸旧域名由下载层按受控候选域名重试，正文只写审核选中的原始候选 URL。正式发布一律由发送脚本把远程图本地化上传：首次创建必须用支持 Markdown 本地图片的 `lark-cli docs +create`，原地更新必须用 `lark-cli docs +update`，不得使用不保证本地图片导入的 `drive +import`。发布后必须回读每个已上传飞书图片素材并与 staging 原图做 SHA-256 比对，不能只验证“图片块存在/素材可下载”，因为失败占位本身也可下载。非榜单/非产品条目没图属正常；候选下载或视觉审核失败时保留正文并把图片层记为 `WARN`，不要硬配、不要重跑正文。
6. **取全文（关键）**：优先基于**完整正文**浓缩，把原文已写明的主体、背景、数据提炼出来（例：白鲸"120亿短剧独角兽IPO"，正文写明是印度 Kuku Technologies、估值18亿美元、成立2018、创始人来自IIT——这些必须提炼进日报）。白鲸正文在静态 `<p>`、36氪出海在 `__NEXT_DATA__`，脚本 `extract_article` 已自动取（草稿里带 summary）。WeWe RSS 已退役，不能把它作为正式全文兜底；若未来接入新的公众号通道，未取到全文时只能保留标题级事实，不得自行扩写。
6a. **公众号"只有标题"时的取全文兜底（治"含糊带过"）**：草稿里某公众号条目只有标题、无 summary，多半是图文混排 + 内嵌 base64 大图令正文文字被图片/SVG/长 token 噪声淹没。未来接入并通过验收的新公众号通道，应先剥离 `<svg>`/`<style>`/`data:` 图片块和长 base64/token，再抽正文；仍不能取得可信全文时才退化为标题级保留，并按需求基线 9c 自查是否漏掉重要条目。不得回退调用已退役 WeWe RSS 的本机全文源。
6b. **白鲸聚合短讯拆条**：标题包含 `一句话看出海新鲜事` 的白鲸聚合文，抓取阶段必须按 `1、2、3、...` 拆成独立候选；每条继承原文链接和发布时间，但候选标题、摘要、来源标注独立。拆条后再走关键词、主题准入、去重、打分与成稿筛选，避免整篇聚合文因标题泛化或单链接去重被丢弃。
7. **精选控篇幅**：每赛道取最重要数条，整篇约 ≤30 条；排序优先级 出海/全球 > 有数据或资本动作 > 业务关注提权信号（2e） > 头部主体 > 时效。头部模型关键进展一般短条收录即可，避免挤占更垂直的游戏/短剧/融资条目。
7a. **合格备选补位**：正式 `legacy` 与严格测试版在低于 `sources.yaml` 的 `min_report_items` 时，按草稿原顺序从已通过同一时间窗、业务准入和旧闻门禁的“备选”池补位至硬下限；平衡/高召回测试版按 2g-3b 继续尝试补向 25 条。`partial/title_only`、灰区、排查区、明确 reject 或无关资讯不得补数；所有补位条目照常接受最终 `check_report.py` 全量复核。
8. **去重**：链接精确 + 跨源标题近重复（脚本已做）+ 前 2 天历史 URL 回溯 + 人工核主题级重复。
8a. **事件级旧闻门禁（防转载/延迟报道混入）**：抓取脚本会读取前 45 天历史成稿，按三层规则输出「疑似旧闻/转载复核」证据链；本地日报配置为 `RIBAO_OLD_NEWS_GATE=hard`，硬命中不进入候选。硬拦截条件包括同 URL/同 canonical URL、跨源标题或正文高度相似、具名产品/作品与事件类型一致，以及既有融资/并购/里程碑事件的主体和关键事实一致。具名产品锚点只取书名号或引号明确标出的名称，避免把同公司不同产品误拦。软复核保留需人工核验的部分重合；成稿阶段会再次比对前 45 天正式日报，备选池或人工补充也不能绕过。只有可核验的实质新进展才可以重新上；单纯将“据报/传闻”改写成“确认/官宣”不构成新事件。
8b. **列表页发布时间硬门槛**：白鲸/36氪出海等 `listpage` 必须先进正文页解析发布时间（白鲸 `<time>`、36氪出海 `article:published_time`/`baidu_ts` 等）；能解析的按北京时间窗口过滤并在草稿显示发布时间。日报默认只要当天窗口内内容；人工兜底也只能考虑近 3 天内报道。文章页仍取不到时间的列表页链接，默认不进入精选/备选正式候选，只放进草稿末尾「列表页无时间戳排查」区；只有明确排查时才用 `--include-undated` 调试并标 `⏱无时间戳` 放回候选区。
9. **当前排除方向**：具身/机器人（人形、机械臂、四足、宇树等）与自动驾驶/Robotaxi/Robovan/无人车先不看；"聊天机器人/对话机器人"等 AI 产品照常保留。
9a. **成稿后逐条主题准入复查（治"无关混入"，必做）**：成稿后对每一条再过一遍 2a/2b/2f/9，凡正文主体不属三类的整条删除，删空的赛道连标题一并删。以下为**实际出现过、被误收又必须剔除**的典型（看正文主体，不看是否提到关键词）：电诈/反诈等社会案件（即便提到"社交 App 引流"）、监管约谈/政策解读（如火车票 OTA 约谈、无人驾驶网约车政策误读）、自动驾驶/Robotaxi/Robovan（如曹操出行 RoboX）、半导体/芯片股价行情（如寒武纪创新高）、航天·火箭·卫星·太空算力（如某太空算力天使轮）、普通游戏本/游戏台式机/电竞显示器/鼠标键盘等参数型硬件发布、与娱乐无关的企业人事/董事会变动（如某 VC 加入 SpaceX 董事会）、新闻早报/资讯聚合体（《8点1氪》《早报》等）。
9b. **归类按"公司当前主体业务"，不按创始人/历史背景（治"误排除"）**："世界模型 / world model / AI 视频·世界生成"属娱乐向 AI（内容生成），即便创始团队出身自动驾驶，也按公司现在做的内容生成业务归入创新·AI娱乐或全球融资，不得因创始人背景误判为"自动驾驶"而排除（例：Odyssey 世界模型融资应纳入）。
9c. **重要信息漏检自查（治"该收没收"）**：成稿后对照草稿"备选"池逐项扫一遍，凡符合三类主题、且属于**重大资本动作（显著金额/估值/IPO，如≥1亿美元或头部机构领投）或核心出海赛道（游戏出海、短剧/漫剧出海等）**的条目，不得仅因脚本 score 低、或只有标题级信息而漏掉；若确不收，须有明确理由（重复/超窗/信息不足）。把"重要信息是否被收录"当作与"无关信息是否被剔除"同等的校验标准。
10. **Source 来源收尾**：正文结束后用 `Source 来源` 表统计本期实际采用的来源与条数；不再放“个人社媒”“兴趣产品跟踪”和 appendix。
10a. **单条来源括注（新增硬规则）**：每条资讯正文的最后一个信息点/最后一段末尾必须追加主信息源名称括注，例如 `（IT之家）`、`（36氪）`、`（白鲸出海）`、`（量子位）`。若一条合并多个来源，括注主来源或信息最完整来源即可；来源链接仍保留为条目底部的裸 URL，不改成 Markdown 链接。
11. **正文不写采集信息或内部过程话术**：单条正文只写资讯事实；允许在最后一个信息点末尾保留简短媒体名括注（如 `（IT之家）`），但不写“该条来自/经 WeWe RSS/VVRS/VVRSS/VBRS 抓取/来源为 XXX”“补足观察信号”“以原文为准”“待补全文”“草稿摘要显示”“公开摘要未展开”“该条作为……保留”“后续可继续跟踪”等采集来源、兜底说明、筛选理由或后续动作。
12. **格式硬约束**：URL 保持裸链不转义；不同一级/二级标题之间用独立一行 `<br>` 做真实空行；标题图标、板块顺序、Source 表格式以 `format/格式规范.md` 为准。
13. **输出文件与包体清洁**：同一天只更新同一个 `日报文档/资讯类简报-{月.日}日.md`，不要生成多个成稿文档；运行产物不要写进 `资讯日报-skill/`。默认目录为项目根目录 `日报草稿/`（候选清单）、`日报文档/`（正式日报）、`日报质检/`（质检报告）、`日报状态/`（去重状态）。`资讯日报-skill/` 只保留可复用的规则、脚本、格式模板和源配置。
14. **自动化原则**：定时任务只负责触发本 skill；完整规则必须写在本 skill 与 `format/格式规范.md` 中，不把业务规则复制进本地自动化 prompt。
14a. **成稿超时同次降级**：Codex 成稿进程在独立进程组内运行；超时后终止整个进程组，在同一个工作目录、同一个 run/manifest 内用去掉历史样稿的紧凑 prompt 重试一次，不得启动第二条正式管线。仍失败时固定模板只使用草稿精选与合格备选生成候选稿，并继续运行完整 `check_report.py`；有 FAIL 仍不得发布。每次尝试只记录状态和错误类别，不记录私有正文。
15. **WeWe RSS 已退役（自动化硬规则）**：正式守门器、预抓和手动正式运行都必须令 `RIBAO_EXCLUDE_WEWE=1`，并将状态记录为 `retired`。不得探测、刷新、打开二维码/重登页、发送 WeWe 相关提醒，或让环境变量重新启用它。旧目录、配置和测试代码仅保留为历史证据；新公众号通道必须独立验收，不能借用该旧路径。

## 源分层策略（资源效率最优）
不要试图每日自动爬全部上百个渠道——多数 ROI 很低。按三层用：
- **Tier 1 主力聚合/全文源**：已替你浓缩好或带完整正文的 feed，一个顶一片，自动按标题分流到三大板块：
  - **ai-bot.cn/每日AI资讯**：纯静态，每条"标题+100~200字+来源链接"，覆盖 AI 模型/应用/AI娱乐/融资。
  - **IT之家 RSS**（`ithome.com/rss/`）：60条/带完整正文/带时间戳，**产品粒度细（单个产品发布/更新）**，补"具体产品"维度。
  - **36氪主站 feed**（`36kr.com/feed`）：带数千字完整正文的**深度文**，便于忠实浓缩出信息完整的条目。
  - **Product Hunt**（`producthunt.com/feed`）：每条=一个新产品，最适合"具体产品"维度（英文、偏 SaaS，靠关键词降噪）。
- **Tier 2 垂直补充源**：补 Tier1 覆盖不到的"出海泛娱乐业务/数据"面——游戏出海（PocketGamer/触乐/GameLook）、短剧（DataEye）、出海综合（白鲸出海/36氪出海 listpage）、数据站（Sensor Tower/点点）。RSS/列表页自动 + 公众号人工。
- **Tier 3 选题池**：附件《信息渠道汇总.md》里的即刻/X/领英/播客/Newsletter 等大列表，噪声大且多需登录，**仅作人工选题与深挖灵感，不做每日自动抓**。
- **语鲸 lingowhale**：前端渲染、抓取拿不到内容，定位为人工订阅公众号合集的工具，不纳入自动管道。

|---|---|---|
| **白鲸出海** | 快讯页 `/newsflashes` 列表解析；**正文藏在 `/article` 静态 `<p>` 里**（"请开启JS"只是提示壳），脚本自动取全文（公司名/背景/数据都在正文）并从文章页 `<time>` 解析发布时间。⚠️ 别用 `/feed`（陈旧问答子站）。还转载 DataEye 短剧周榜 | ✅ listpage + 自动取正文 + 发布时间 |
| **36氪出海** letschuhai | 列表解析；**正文在 Next.js `__NEXT_DATA__` 的 `content.rendered`**，脚本自动取全文，并从 `article:published_time` / `baidu_ts` 等 meta 字段解析发布时间 | ✅ listpage + 自动取正文 + 发布时间 |
| **36氪主站**（快讯/融资） | SPA，公开 RSSHub 被封(403)；需自建 RSSHub 用 `/36kr` 路由 | ⚠️ 待自建 |
| **DataEye** | 官网 SPA、短剧数据在 JS/登录后，简单抓取拿不到；周榜常被白鲸转载可间接获取，或 Chrome 渲染/找 API | ⚠️ 公众号/间接 |
| **短剧自习室** | 纯公众号、无官方 API | ⚠️ 人工补链 |

结论：**白鲸出海 + 36氪出海** 两个 listpage 源已能稳定自动覆盖出海泛娱乐七七八八（实测合计 60+ 条/天，含游戏买量、海外短剧榜单、出海数据），且会进文章页补发布时间用于窗口过滤；DataEye/短剧自习室作公众号人工补充；36氪主站待自建 RSSHub。

## 每日执行流程（agent 按此走）

0. **WeWe RSS 状态输入**：正式定时和手动运行一律写入 `RIBAO_EXCLUDE_WEWE=1`、`RIBAO_WEWE_STATUS=retired`；不得自行探测、等待登录或发送提醒。
1. **抓取**：运行 `python fetch_news.py`，默认生成 `../日报草稿/资讯日报-草稿-YYYYMMDD.md`（候选清单 + 公众号待补清单 + 告警）。不要用 `--hours 24` 跑正式日报；`--hours` 仅用于临时测试，否则会偏离北京时间 15:00—15:00 窗口。历史日期测试用 `python fetch_news.py --date YYYYMMDD`。
2. **补公众号**：草稿里"⚠️ 公众号待人工贴链接"列出的源，让用户把当日链接/正文贴进来（公众号无官方 API，这步暂时人工）。其它公开网页若需补充可用 web 检索/抓取。
3. **筛选**：从候选里挑出符合三大板块、有信息量的条目；去重、去边角料。出海/全球/融资优先。草稿里的 ⭐精选 是默认采用清单，成稿时必须逐条覆盖校验；若某条不采用，只能因为跨源/跨日重复、超出时间窗、与主题明显无关或信息质量不足，并在工作中明确剔除原因，不能因为摘要短、公众号正文未展开或赛道较短而直接漏掉。若只拿到标题和链接，保留标题级事实并避免扩写。
4. **取全文**：白鲸/36氪出海的正文由脚本 `extract_article` 自动抓取（草稿里已带 summary，含主体/背景/数据）。公众号新通道通过独立验收前只允许人工补全；务必基于正文写，若只有标题和链接，正文只写标题能支撑的事实，不写采集说明或兜底话。
5. **浓缩排版**：逐条按 `format/格式规范.md` 套模板，**忠实浓缩原文、不加自己的解读**——
   - **模板 A 分维度标签型**：产品/财报类、信息维度多的业务资讯。
   - **模板 B 概述段落型**：单点消息。
   - **模板 C 融资型**：两段叙述，全部融资条目用，归入「全球融资」板块。
   - 每条：简明标题 → 正文（按信息量浓缩，通常 200–400字；最后一个信息点末尾加 `（来源名）`）→ 原文链接（必带）。
6. **组装**：复制 `format/日报模板.md` 骨架，填入各条，删掉当日无内容的赛道，结尾补 `Source 来源` 表（只统计最终成稿正文实际采用的来源与条数）。
7. **生成后质检**：成稿后运行 `python check_report.py --draft ../日报草稿/资讯日报-草稿-YYYYMMDD.md --report ../日报文档/资讯类简报-{月.日}日.md --write ../日报质检/资讯日报-质检-YYYYMMDD.md`。质检报告留在 `日报质检/`，不进入最终日报正文。
8. **修复再确认**：若质检出现 `FAIL`，必须先修正成稿再重新运行质检；`WARN` 需要人工回看草稿摘要/原文链接确认。只有质检无 `FAIL` 才算完成。
8a. **精选剔除审计**：正式 `legacy` 成稿阶段若合理剔除草稿中的 ⭐精选，必须逐 URL 写入 `<!-- QA_SKIP 原文URL | 简明且可核验的理由 -->` 质检注释，不得静默遗漏。该注释只在质检阶段存在；由质检器持久化审计记录，通过后再由受控发布器从最终 Markdown/飞书文档自动剔除。测试 v2 的候选取舍已在上游完成，写作模型不得以 QA_SKIP 自行改写必交集；需剔除的条目必须回到候选审核层重新生成冻结草稿。
9. **产出**：保存/更新当天唯一的 `日报文档/资讯类简报-{月.日}日.md`，不要另起多个成稿文件；草稿、质检和状态文件也不要写回 `资讯日报-skill/`。
9a. **重试草稿复用门禁**：守门器重试时，只允许复用对应 `run-manifest` 中 `fetch=ok` 的已冻结草稿。抓取/公开源覆盖门禁失败时留下的草稿只作审计证据，不得在后续重试中当作健康草稿复用。
10. **写入飞书（本地自动化必做）**：定时任务应通过项目根目录的 `run_daily_with_feishu.sh` 收尾。当前生产采用**索引交付模式**：`FEISHU_DOC_ONLY=1`、`FEISHU_DAILY_INDEX=1`、`RIBAO_GROUP_MESSAGES=0`；质检为 `PASS` 或 `WARN` 时，用 `lark-cli` 的 `user` 身份创建/原地更新当天 Docx，并向战略小组授予 `full_access`（可管理），不发送任何群消息；随后幂等更新固定索引文档，并再次向战略小组授予 `full_access`。日报正文或索引的授权失败时整次交付不得标记成功；该模式不要求 bot 留在群内。代码仍保留显式开启的群消息模式作为可选能力，但不得在当前生产配置中启用。
10a. **测试索引隔离**：`run_daily_test.sh` 只更新独立的测试日报索引。每个日期只占一行，固定列为日期、`测试版v2-严格`、`测试版v2-平衡`、`测试版v2-高召回`、公开源、公众号源、质检结果、生成时间；三种策略只展示各自最新日报链接，旧测试记录保留在本地但不展示。三个版本必须使用同一批当日来源；公开源、公众号源、质检结果和生成时间都是当天整体状态，不得再按严格/平衡/高召回重复拆分。公开源和公众号源分别记录抓到、精选、候补、最终采用文章数，公众号源还必须标明当天是否启用及覆盖 `x/27`。不得展示运行标签或内部策略名。生成失败或质检拦截也必须登记。它不得触碰正式索引、不得发送群消息；三份测试日报单篇文档与测试索引都必须向战略小组授予 `edit`（可编辑）且不触发通知，不授予测试日报可管理权限。任一测试日报或索引授权失败时测试流程必须失败并保留本地证据。矩阵在冻结快照后可执行**一次**共享 Codex 候选审核：已通过项可被剔除、完整灰区项只能在对应版本提权；审核限时 90 秒，超时、鉴权失败或输出校验失败均记录 `fallback` 并直接沿用原生筛选，绝不阻塞三版并行生产或正式日报。融资速览只读取同批、可追溯的资料；自动模式无联网检索，原文未证实的业务/估值必须如实写未披露。

## 升级路径
- **第一阶段（当前）**：半自动。公开 RSSHub 实例 + 各站 RSS 自动抓，公众号人工贴。
- **公众号自动化**：已退役 WeWe RSS 的目录、配置和运行记录仅保留审计，不得进入正式日报。后续接入任何新公众号通道，必须先完成独立的来源新鲜度、全文完整度、去重和风控验收，再决定是否进入生产；在此之前保留人工补链兜底。
- **第二阶段（RSSHub）**：自建 RSSHub（Docker/VPS），把 `sources.yaml` 的 `rsshub_base` 改成自建地址，提升 36氪主站等 RSSHub 路由的稳定性。
- **融资增强**：点点数据 API 上线后，在 `.env` 填 `DIANDIAN_API`，把对应源 `enabled: true`，扩展脚本 api 分支。

## 注意
- 公众号抓取无官方 API，任何第三方方案都可能失效，始终保留"人工贴链接"兜底。
- 抓取仅用于内容聚合，遵守各站 robots 与版权，简报中保留原文出处链接。
